## 1. Objective

Build the Next.js admin dashboard shell and every control-plane screen from `architecture.md §12`:
authentication with TOTP, company onboarding with one-time credential reveal, per-tenant settings,
device management, and the audit log viewer.

At the end of this task **a company can be onboarded entirely through the UI**, and the credentials
handed to a client come from a screen rather than a `curl` command.

---

## 2. Scope of work

### In scope
- Next.js 15 App Router app, Tailwind + shadcn/ui, design tokens, light/dark.
- Generated, typed API client from `docs/openapi.yaml`; auth-aware fetch with refresh handling.
- Login → TOTP → session; enrolment flow; session list; logout/logout-all.
- Companies: list, create wizard, detail, settings form, status actions, readiness checklist.
- Credentials: issue/revoke/rotate with one-time reveal UX; webhook secret rotation; webhook test.
- Devices: list with health, detail, rename, block/unblock/retire, force-sync, token rotate.
- Audit log viewer with filters.
- Onboarding packet download.
- Shared UI kit: data table (server-side cursor paging, filters in URL), forms with server-error
  mapping, toasts, confirm dialogs for destructive actions, empty/loading/error states, a11y baseline.

### Out of scope
- Transactions, reviews, webhooks-monitoring, analytics screens → Task 12.
- Merchant-facing portal → post-v1.
- Any business logic in the frontend — the dashboard is a thin client over the Task 04 API.

## 4. Implementation steps

### 4.1 App scaffolding
1. `apps/admin` — Next.js 15 App Router, TypeScript strict, Tailwind, shadcn/ui, `next/font`.
2. Route groups: `(auth)/login`, `(auth)/2fa`, `(dash)/…` with a shared authenticated layout
   (sidebar + topbar + breadcrumb + environment badge — a coloured **STAGING/PRODUCTION** badge is not
   decoration; it prevents suspending a real client while testing).
3. Server components for data fetching where possible; TanStack Query for interactive/polled views.
4. `lib/api-client.ts` generated by `openapi-typescript` + a thin typed fetch wrapper:
   - attaches the access token from an in-memory store,
   - on 401 → single-flight refresh via the `httpOnly` cookie → retry once → else redirect to login,
   - maps the Task 03 error envelope to `{code, message, details, requestId}` and surfaces
     `requestId` in error toasts (so a support conversation can reference it).
   - `pnpm --filter admin api:generate` regenerated in CI; drift fails the build.

### 4.2 Token handling (security-critical)
- Access token **in memory only** (React context/Zustand) — never `localStorage`/`sessionStorage`
  (XSS would exfiltrate it). Refresh token stays in the `httpOnly; Secure; SameSite=Strict` cookie
  set by Task 04.
- On hard reload, the app silently refreshes to recover a session.
- `middleware.ts` guards `(dash)` routes by refresh-cookie presence (a fast redirect, not the real
  authorization — that is server-side in Task 04).
- Idle timeout: 30 minutes of no activity → clear the in-memory token and prompt for re-login;
  absolute session end honours the refresh expiry.
- No secret value is ever written to component state longer than needed, or to any analytics/error
  reporter — Sentry (Task 16) gets a `beforeSend` scrubber for anything matching the key prefixes.
- CSP header (`next.config.ts`): no `unsafe-inline` scripts, `connect-src` limited to the API origin.

### 4.3 Auth screens
1. **Login** — email/password; distinct handling for `mfa_required` vs `enrolment_required` vs
   locked (`locked_until` shown as a countdown) vs rate-limited (`Retry-After` countdown).
2. **TOTP enrolment** — QR (rendered client-side from the `otpauth://` URI; no external QR service),
   manual secret fallback, verify field, then the 10 recovery codes with **copy** and **download**
   plus a mandatory "I have stored these" confirmation.
3. **TOTP verify** — 6-digit input with auto-advance/paste support, "use a recovery code" link,
   clear error for drift vs reuse.
4. **Sessions** — list (IP, UA, created, last used, current marker), revoke one, revoke all.
5. **Change password** — current password + fresh TOTP code; explicit warning that other sessions end.

### 4.4 Companies
1. **List** — server-side cursor paging, search, status filter; columns: name, code, status,
   devices online/total, pending orders, verified today, open reviews, webhook health dot.
   Filters/sort/cursor live in the URL so a view is shareable and survives reload.
2. **Create wizard** (3 steps):
   - details (name, contacts, notes, default callback URL),
   - settings (grouped by matching / webhook / retention / limits, each with an inline explanation of
     what the knob actually does — this form is where a misconfiguration silently costs a client money),
   - review & create.
   On success → **one-time reveal screen**: company code, server key, device enroll key, webhook
   secret, each with copy buttons, a masked-by-default toggle, and an unmissable
   "these are shown once" warning. A "Download onboarding packet" button (Task 04 endpoint) and a
   blocking confirm ("I have saved these credentials") before navigating away.
3. **Detail** — tabs: Overview (readiness checklist from Task 04, 30-day stats), Settings, Credentials,
   Devices, Webhook.
   - **Readiness checklist** is the primary onboarding UX: settings valid → server key → enroll key →
     webhook secret → device enrolled → heartbeat received → webhook test passed, each with a direct
     action link for the unfinished step.
4. **Settings form** — typed from OpenAPI, client-side bounds mirroring Task 04's server bounds,
   server validation errors mapped to fields, dirty-state guard, diff summary before save
   ("order TTL 60 → 30 minutes"), and a note that changes do not affect existing orders.
5. **Status actions** — suspend / disable / reactivate behind a typed-confirmation dialog
   (type the company code, as in GitHub's delete flow) with a required reason, and inline text stating
   exactly what will happen (`SUSPENDED`: SMS still ingested, orders rejected, webhooks paused;
   `DISABLED`: everything stops, device tokens revoked). Misunderstanding this is a client outage.

### 4.5 Credentials
- List with type, prefix, label, scopes, last used (relative + absolute on hover), expiry, state.
- Issue → one-time reveal modal (same component as the wizard).
- Revoke → confirm; the "last active server key" case surfaces the Task 04 force requirement with an
  explicit warning that the client's website will stop working.
- Rotate → choose grace hours (0/24/72) with an explanation, then reveal the new key.
- Webhook secret rotate → warns about the 7-day dual-signing window and shows when the previous
  secret expires.
- **Webhook test** button (Task 09 `/webhooks/test`) → shows status, latency, response excerpt, the
  signature header sent, and the expected `v1`, with a copy-for-support block. This is the button that
  ends most integration support threads.

### 4.6 Devices
- List: name, company, online dot (with last-heartbeat relative time), model, app/Android version,
  battery, permission state, battery-opt state, queue depth, clock skew, flags. Filters: company,
  online/offline, status, has-flags. Auto-refresh every 30 s.
- Detail: telemetry panel, recent `device_events` timeline (Task 06), recent SMS from that device,
  and action buttons: rename, set wallet number, block/unblock, retire, force-sync, rotate token.
- Directive feedback: after force-sync, show "queued — will apply at the next heartbeat (≤15 min)"
  and reflect completion once consumed, so support isn't left guessing.
- An **offline device banner** at the top of the dashboard listing any device offline >30 min during
  Dhaka business hours — the single most operationally important thing on the screen
  (`architecture.md §15.3`).

### 4.7 Audit log
Filters (actor, action, entity type/id, company, date range), cursor paging, expandable
before/after JSON diff with redaction markers preserved, copy-`request_id`, and a per-entity
"history" link reachable from company/device/key screens.

### 4.8 UI kit & quality baseline
- `DataTable` (server cursor paging, URL-synced state, column visibility, empty/loading/error),
  `ConfirmDialog` (typed confirmation variant), `SecretReveal`, `CopyButton`, `StatusBadge`,
  `RelativeTime` (absolute on hover, Dhaka + local), `Money` (never renders a float),
  `FormField` with server-error mapping, `PageHeader`, `EmptyState`, `ErrorState` (shows `requestId`).
- a11y: keyboard-navigable tables and dialogs, focus traps, labelled inputs, visible focus rings,
  AA contrast in both themes, `aria-live` on toasts.
- Loading: skeletons, no layout shift; every mutation optimistic-free (money screens should show
  server truth, not optimistic guesses).

## 6. Testing & validation

| What | How |
|---|---|
| **Playwright E2E — onboarding** | Against a real API + seeded DB: login → enrol TOTP (generate codes with a TOTP lib in the test) → create company → capture revealed credentials → use the server key in a raw request to `/payments/register` → assert 201. This single test proves the whole control plane works end to end. |
| Auth edge cases | Wrong password; locked account countdown; rate-limited; wrong TOTP; reused TOTP; recovery code; expired access token mid-session (refresh happens transparently, exactly once for parallel requests); revoked refresh token → redirect to login; idle timeout. |
| Token hygiene | Assert no token in `localStorage`/`sessionStorage` (evaluate in the browser context); assert the refresh cookie is `httpOnly` (unreadable via `document.cookie`); assert no secret appears in any Sentry payload (stub transport). |
| One-time reveal | Credentials shown once; navigating away and returning shows no secret; the confirm gate blocks accidental navigation; copy buttons place the exact value on the clipboard. |
| Settings form | Out-of-bounds values blocked client-side **and** server errors mapped to the right field when bypassed; diff summary correct; dirty-state guard works. |
| Status actions | Typed confirmation required; reason mandatory; after suspend, the UI reflects it and the explanatory text matches actual backend behaviour (cross-checked against the Task 04 test expectations). |
| Devices | Online/offline derivation matches the API at boundaries; force-sync shows queued then consumed; offline banner appears when a device's heartbeat is aged (seed the DB accordingly) and respects Dhaka business hours. |
| Webhook test | Success and failure paths render usefully; a deliberately mis-signing receiver produces a readable diagnosis. |
| Audit viewer | Filters work; redaction markers visible; no secret values rendered. |
| a11y | `@axe-core/playwright` on every route, zero serious/critical violations; full keyboard walkthrough of the create-company wizard and one destructive dialog. |
| Client/contract drift | `api:generate` produces no diff in CI; a deliberate backend field rename fails the admin build. |
| Visual/UX | Manual pass at 1280×800 and 1440×900, light and dark; long company names, empty states, 500-row tables; slow-network simulation (3G throttling) shows skeletons rather than layout jumps. |

**Smoke demo:** onboard a real-looking company entirely in the browser, download its onboarding packet,
and show the readiness checklist advancing as you enrol a device (from Task 06's `curl` or the app) and
run the webhook test.

## 7. Acceptance criteria

- [ ] A company is onboarded end-to-end through the UI, producing usable credentials, with the one-time reveal enforced and the packet downloadable.
- [ ] Login + TOTP enrolment/verification + recovery codes + session management all work, including every negative case in §6.
- [ ] Access token lives in memory only; refresh cookie is `httpOnly` and unreadable from JS; both asserted by tests.
- [ ] Parallel 401s trigger exactly one refresh; refresh failure redirects to login without a loop.
- [ ] Company settings form mirrors server bounds, maps server errors to fields, and shows a change diff.
- [ ] Suspend/disable/reactivate require typed confirmation + reason and describe their real effects accurately.
- [ ] Credential issue/revoke/rotate and webhook-secret rotation work with correct warnings; last-server-key revoke is guarded.
- [ ] Webhook test surfaces status, latency, body, sent signature, and expected value.
- [ ] Device list/detail show real health; block/unblock/retire/force-sync/rotate work; directive state is visible; the offline-device banner works.
- [ ] Audit viewer filters correctly and never renders secret material.
- [ ] All routes pass axe with zero serious/critical violations and are keyboard operable.
- [ ] OpenAPI client generation is drift-checked in CI; Playwright suite runs in CI against a seeded API.
- [ ] `docs/admin-guide.md` covers daily operation of these screens.

## 8. Risks & notes

- **The one-time reveal is the highest-stakes UI in the product.** If an admin navigates away before
  saving the keys, the only recovery is rotation — which for a live client means downtime. Hence the
  blocking confirm, the download button, and the copy buttons all existing before this task is done.
- Keep the dashboard a thin client. Any validation implemented here must also exist server-side
  (it does — Task 04); duplicating *logic* rather than *bounds* is how the two drift.
- The environment badge and the typed-confirmation dialogs exist because the same person operating
  staging operates production. That is a real, likely failure mode for a one-operator platform.
- Don't build a merchant-facing view "while we're here". It changes the auth model (per-company
  users), which is explicitly post-v1 (`architecture.md §19`).
